# Contexto del cambio

- Objetivo: retirar credenciales planas/globales de nodos y garantizar restauración, mutación y transporte bajo identidad vigente, sin perder el legado.
- Actor: usuario autenticado en main; el servicio deriva identidad y nunca acepta propietario efectivo desde renderer/runtime.
- Alcance: almacén cifrado por propietario reutilizando os-cipher/private-files, archivo legado cifrado recuperable, sesión/colas de persistencia y revocación del servicio, contexto del host entrante y aviso de migración en panel.
- No objetivos: certificar identidad SOFIA/RLS o roles organizacionales, reasignar huérfanos automáticamente, sanear datos arbitrarios del nodo o resolver todos los canales Computer Use/Desktop Agent.
- Restricciones: rama acumulativa, respaldos relativos contra unidad 39, sin tocar datos/secretos reales/.env, sin GUI ni acciones/red/cuentas reales, sin stage/commit/push. Fuentes finales congeladas durante compuerta y build.
- Contratos: mismos canales; revisión de configuración pasa a async por restauración segura. Cada operación del servicio obtiene identidad main y espera persistencia antes de publicar. Estado de migración aditivo sin credenciales; archivos versionados cifrados con propietario exacto.
- Riesgo/HITL: alto. Host nuevo deshabilitado y sin acceso anónimo. Cambiar cuenta invalida inmediatamente revisiones, transporte y host previo. El legado completo se preserva cifrado; sólo nodos con owner_user_id exacto se importan. Host sin propietario y nodos huérfanos exigen nuevo emparejamiento, mediante HITL existente. No asignar credenciales de otra cuenta.
- Criterios: no tokens en archivos privados o temporales; sin fallback plano/cwd; error de cifrado/archivo inválido conserva versión previa; identidad A/B/A/logout/navegación impide publicación obsoleta; no éxito antes de guardar; fallo no cambia RAM; migración idempotente y archivo privado existente gana; host previo no admite efectos tras cambio de sesión; cuotas/errores seguros y pruebas reales de filesystem con datos propios.
- Incertidumbres: no se conoce propietario del host legado ni de registros sin owner. No inventarlo; conservar archivo cifrado para recuperación/re-emparejamiento. La protección del SO no aísla frente a otro proceso con autoridad completa del mismo usuario del SO. Una operación ya enviada o rename ya admitido puede terminar; colas del almacén evitan sobrescribir sesiones posteriores y no se promete rollback físico.
