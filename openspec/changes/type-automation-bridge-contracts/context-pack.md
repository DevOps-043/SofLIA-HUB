# Contexto del cambio

- Objetivo: retirar el principal foco de any público y duplicación de contratos en automatización local, Desktop Agent y nodos remotos, conservando integración y modularidad.
- Actor: consumidor renderer y servicios main/preload; no se conceden herramientas o permisos nuevos al runtime.
- Alcance: DTO canónicos puros derivados de implementaciones actuales, APIs públicas tipadas, tipos main reexportados donde proceda, respuestas remotas tratadas como datos desconocidos y comprobadas antes de usar metadata, wrappers y pruebas de contratos/compatibilidad.
- No objetivos: cambiar canales/argumentos válidos, implementar aislamiento de propietarios o cifrado de nodos, rediseñar HITL/autorización de automatización, ejecutar herramientas nativas, red/cuentas reales o reducir any privados mediante casts ficticios. El coordinador de navegador sigue pendiente; su tamaño no se reduce moviendo código sin cohesión.
- Restricciones: rama/worktree acumulativos; preservar cambios anteriores/otros worktrees, secretos/.env y configuración local. Sin stage/commit/push, SQL o GUI. Una sola compuerta final con cobertura y build; negativas dirigidas durante implementación.
- Contratos: Computer Use/desktopAgent/remoteNode conservan nombres y canales. Las respuestas dinámicas de herramientas son objetos de datos desconocidos, no any; status/config/tareas/perfiles y registros tienen tipos derivados de productores reales. Opciones de tarea IPC no incluyen AbortSignal, que sólo pertenece a llamadas internas main.
- Riesgo: medio/alto por alcance de contratos. Tipos no equivalen a validación de fuente/HITL. Hallazgo confirmado: varias rutas nativas confían sólo en sesión o no comprueban emisor; confirmación de acciones peligrosas se decide en renderer antes de executeToolDirect. Un emisor con puente y sesión podría eludir esa confirmación. Se registra explícitamente como deuda pendiente, sin atribuir remediación a este refactor.
- Criterios: sin any en las tres interfaces públicas; mismos argumentos y resultados válidos en cuatro capas; main/renderer comparten DTO sin imports runtime cruzados; respuestas HTTP no objeto o metadata malformada no corrompen estado; consumidores compilan sin nuevos escapes any/supresiones; pruebas, cobertura, build y lint sin deuda nueva; medir reducción real de errores y no inventar porcentaje global.
- Incertidumbres: respuestas de nodos terceros pueden contener campos adicionales; preservarlos como unknown y conservar capacidades futuras válidas como strings. RLS, permisos de servidor, fallback remoto y seguridad completa de automatización mantienen su frontera.
